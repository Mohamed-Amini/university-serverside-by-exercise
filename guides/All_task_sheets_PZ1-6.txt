Цель: спроектировать архитектуру БД предметной области и реализовать базовые

3. Заполнить каждую таблицу не менее чем 10 записями.

3. Продемонстрировать INNER, LEFT, FULL OUTER, CROSS JOIN.
4. Сгенерировать не менее 10 000 записей в одной или нескольких таблицах.
5. Выполнить типовой SQL -запрос приложения с использованием связей.
Критерии приёмки
☐ FK и ограничения целостности в DDL

Стек: PostgreSQL, generate_series / COPY / Java Faker.

Подготовка
 ПЗ1 выполнено: таблицы и базовые данные созданы.
 Определены виды связей (1:1, 1: N , M : N ) для вашей модели.
Пошаговая реализация
Шаг 1. Анализ и выбор типов связей
Цель: для каждой пары таблиц определить корректный тип связи до написания FK .
Используем: ER -диаграмма из ПЗ1
Разметьте связи: один-ко-многим ( FK в таблице «многие»), один-к-одному ( FK + UNIQUE ),
многие-ко-многим (промежуточная таблица с двумя FK ). Запишите решения в отчёт.
Шаг 2. Реализация внешних ключей
Цель: обеспечить ссылочную целостность на уровне БД.
Используем: ALTER TABLE, REFERENCES, ON DELETE
Добавьте FK - constraint к существующим таблицам. Выберите ON DELETE RESTRICT , CASCADE
или SET NULL в зависимости от бизнес-логики.
ALTER TABLE book
ADD COLUMN author_id INTEGER
REFERENCES author(id)
ON DELETE RESTRICT;
Шаг 3. Демонстрация JOIN -запросов
Цель: показать различия между типами соединений на реальных данных.
Используем: INNER JOIN, LEFT JOIN, FULL OUTER JOIN, CROSS JOIN
Напишите по одному запросу для каждого типа JOIN . Прокомментируйте, чем отличается
результат (какие строки попадают, какие отсеиваются).
-- INNER: только совпадающие
SELECT a.name, b.title
FROM author a
INNER JOIN book b ON b.author_id = a.id;
-- LEFT: все авторы, даже без книг
SELECT a.name, b.title
FROM author a
LEFT JOIN book b ON b.author_id = a.id;

Шаг 4. Массовая генерация данных
Цель: заполнить таблицы ≥10 000 записями для последующих нагрузочных тестов.
Используем: generate_series, random(), md5(); или COPY FROM CSV; или Java Faker
Сначала сгенерируйте родительские сущности, затем дочерние с корректными FK .
generate _ series удобен для PostgreSQL ; Faker — если нужны правдоподобные строки.
INSERT INTO book (title, author_id)
SELECT
md5(random()::text),
(1 + floor(random() * 100))::int
FROM generate_series(1, 10000);
Шаг 5. Типовой запрос приложения
Цель: сформулировать запрос, который реально мог бы выполнять ваше приложение.
Используем: JOIN , WHERE , ORDER BY
Придумайте сценарий (например, «список книг автора с фильтром по году») и реализуйте
его одним SQL -запросом с использованием связей.
SELECT b.title, b.year, a.name AS author
FROM book b
JOIN author a ON a.id = b.author_id
WHERE b.year >= 1900
ORDER BY b.year DESC;

Используем: generate _ series , COPY , отключение индексов на время загрузки

Шаг 2. Формулировка типового тяжёлого запроса
Цель: получить запрос, который соединяет ≥3 таблицы и фильтрует по ≥3 условиям разных
типов.
Используем: JOIN , WHERE (строки, числа, даты)
Составьте запрос, имитирующий реальную нагрузку: несколько JOIN , фильтрация по
строке, числу и дате, сортировка или LIMIT .
SELECT a.name, b.title, b.year
FROM book b
JOIN author a ON a.id = b.author_id
JOIN category c ON c.id = b.category_id
WHERE a.name LIKE 'A%'
AND b.year BETWEEN 2000 AND 2020
AND c.code = 'FICTION'
ORDER BY b.year DESC
LIMIT 100;

Шаг 4. Создание и перестройка индексов
Цель: добавить индексы на столбцы из WHERE и JOIN , затем перестроить их.
Используем: CREATE INDEX , REINDEX
Создайте индексы по одному, каждый раз повторяя EXPLAIN ANALYZE . После массовой
загрузки выполните REINDEX для актуальной статистики.

CREATE INDEX idx _ author _ name ON author ( name );
REINDEX INDEX idx _ book _ year ;
Шаг 5. Замер «после оптимизации» и таблица результатов
Цель: сравнить производительность и сформулировать выводы.
Используем: EXPLAIN ANALYZE , таблица в отчёте
Повторите EXPLAIN ANALYZE с полным набором индексов. Заполните таблицу: какие

Scan / Index Scan / Bitmap Scan ).

Шаг 7. Сервисный слой и @ Transactional
Цель: вынести бизнес-логику из контроллера в сервис и обеспечить атомарность
операций, затрагивающих несколько сущностей.
Используем: @ Service , @ Transactional , propagation REQUIRED
Создайте AuthorService с методом, выполняющим несколько изменений в БД (например,
создать автора и несколько связанных книг). Пометьте метод @Transactional — при
RuntimeException все изменения откатятся.
@Service
@RequiredArgsConstructor
public class AuthorService {
private final AuthorRepository authorRepo;
private final BookRepository bookRepo;
@Transactional
public Author createAuthorWithBooks(Author author, List<Book> books) {
Author saved = authorRepo.save(author);
books.forEach(b -> { b.setAuthor(saved); bookRepo.save(b); });
return saved;
}
}
Шаг 8. Демонстрация rollback

ошибки — данные должны появиться.
@Transactional
public void transferDemo(Long fromId, Long toId, BigDecimal amount) {
Account from = accountRepo.findById(fromId).orElseThrow();
Account to = accountRepo.findById(toId).orElseThrow();
from.debit(amount);
to.credit(amount);
// throw new RuntimeException(\\"test rollback\\");
accountRepo.save(from);
accountRepo.save(to);
}
